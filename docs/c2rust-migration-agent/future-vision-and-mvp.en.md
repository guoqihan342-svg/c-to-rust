# Future Vision and MVP Roadmap

Chinese original: `future-vision-and-mvp.md`.

## 1. Goal

Build an end-to-end MVP pipeline: `input.c` → `c2rust-migrator` → `output.rs`. Phase 1 proof is complete in the code path sense (the FlashDB `real-fdb-calc-crc32` named slice can generate a compilable Rust candidate through real clang AST dump lowering + typed IR + generic emitter and bind it to semantic gates through accepted evidence), and committed evidence now includes a durable real-clang lowering artifact. Generated drafts remain candidates, and significant gaps remain before reaching an industrial-grade C→Rust translator.

The boundary must stay explicit: `validation/evidence/*/l1-native-build.json` only proves the original C project builds or smoke-tests in a pinned environment. It does not prove Rust translation success. Current real auto-translation capability is still concentrated in curated function slices; the large-project evidence catalogue is an input pool and baseline, not proof that real large projects can already be translated.

## 2. IR Layering Design (Recommended Industrial Standard)

Key principle: **IR must not "decide how Rust should be written"; it must only "describe what C is"**. Correctness comes from C oracle; IR is the intermediate representation that faithfully describes C semantics.

### Layer 1: Semantic IR (Most Important)

**Preserve C semantics. Do not do Rust inference. Do not produce candidates.**

This layer is the translator's core asset. It only answers: "What does this C code do in the C abstract machine?"

- Every C operation preserves its original semantics: integer promotion rules, usual arithmetic conversions, sequence points, lvalue conversions
- No premature judgment on "this pointer can become a slice" or "this struct can become a Rust struct"
- Preserve raw pointer arithmetic, implicit casts, truncation, and promotion information
- Array-to-pointer decay is part of C semantics and must be preserved in the IR
- UB markers (locations of undefined behavior) must also be recorded at this layer

**Current status**: Our typed IR mixes in some Rust inference (e.g., directly marking `const void *` as `&[u8]`). This is acceptable for P0 but should be separated into a dedicated Lowering layer long-term.

### Layer 2: Control IR

**if / loop / goto / switch, with explicit CFG.**

- Control flow transitions from AST to explicit basic blocks + CFG
- `if-else`, `while`, `for`, `do-while`, `switch-case`, `goto`/label all enter a unified CFG
- Each edge carries an explicit condition (or is unconditional)
- `break` and `continue` map to CFG edges; no ad-hoc handling needed
- Support relooper (recovering high-level structured control flow from arbitrary CFG), which is prerequisite for translating `goto` / `switch`

**Current status**: We have a basic `cfg.json` evidence template, but typed IR internally still uses AST-style control flow (`If`, `While`, `For`, `DoWhile`). Rust candidate lowering for `switch`, `goto`, and computed goto is still unsupported. The legacy compatibility path has started recording minimal CFG/fail-closed evidence for label/goto/switch/case/default, but that is not full Control IR and does not replace clang AST / typed-IR fixture replay, route evidence, or a relooper.

### Layer 3: Typed Value IR

**integer / pointer / struct / array, explicit casts only.**

- All implicit type conversions (integer promotion, usual arithmetic conversion, array-to-pointer decay, function-to-pointer decay) become **explicit casts** at this layer
- Pointer arithmetic is decomposed into element access: `p + i` becomes `element_at(p, i)` or equivalent
- Struct field access is explicit offset-based or symbolic field access
- Array indexing is explicit base + offset
- The type system only describes C runtime behavior; no Rust type inference

**Current status**: Our typed IR has `Cast { implicit }` to distinguish explicit/implicit casts, integer types have signed/width information, and pointers have `Pointer { pointee }`. The clang frontend now tightens unknown/missing `ImplicitCastExpr.castKind` to `Unsupported`/fail-closed, modeled `IntegralCast`/`IntegralPromotion` nodes can be preserved as explicit IR casts in ordinary value contexts, binary usual-arithmetic contexts, unary-plus integer-promotion contexts, direct-call argument contexts, `?:` condition contexts, and `if`/`while`/`do-while`/`for` condition contexts, integer `NoOp` in preserved value contexts is preserved as an explicit `implicit=true` IR cast, and explicit C-style same-width integer `NoOp` casts remain explicit `implicit=false` casts. Ordinary expression-position `ArrayToPointerDecay` and ordinary value/argument-position `FunctionToPointerDecay` now lower into explicit typed IR as `IrExpr::ArrayToPointerDecay` / `IrExpr::FunctionToPointerDecay`; unary deref of a direct complete fixed array DeclRef lowers to `array[0]`, restricted `*(array + integer_expr)` lowers to `array[index]`, while other ordinary expression, pointer-value, or function-pointer-value shapes still fail closed during Rust emission or bounded-call validation without explicit lowering evidence. Clang-proven integer value-context `LValueToRValue` is now preserved as an explicit typed IR `IrExpr::LValueToRValue` node; this currently covers only integer scalar reads such as `return value;`. Pointer, record, and general lvalue reads must still use existing narrow dedicated paths or fail closed without ownership, lifetime, alias, layout, or provenance lowering evidence, and non-integer/non-preserved `NoOp` remains a limited transparent skeleton boundary. It still does not route every implicit cast through one unified Semantic IR node; array/function decay lowering, non-integer conversions, and full conversion discipline across parameters, returns, and compound assignments still need further formalization.

### Lowering Layer (from Semantic IR to Rust candidate)

This layer converts "describing C" into "generating Rust". Key principles:

1. Do not modify the Semantic IR itself
2. Every lowering rule must be provable (supported by C oracle or typed evidence)
3. When lowering fails, preserve the complete fail-closed reason
4. No "guessing" allowed — if C semantics cannot be safely mapped to safe Rust, refuse translation

Typical lowering rules:
- `const T *p` + read-access evidence (`*p` / `p[i]` / `*(p+i)` / `*p++`, etc.) → `p: &[T]` (must prove: an actual read access exists, no writes, no escape, bounded lifetime, and inferrable length/index bounds; an unused or declared-only readonly pointer parameter fails closed and must not auto-lower)
- `T *out` + write-only access → `out: &mut [T]` (requires noalias proof; if the same function also reads from readonly `const T *`, there must be explicit `restrict`/noalias/escape facts, and `const` alone must not imply non-aliasing)
- `uint32_t + uint8_t` → explicit `(byte as u32) + acc` (requires promotion proof)
- `while(size--)` → Rust `loop` + `wrapping_sub` (must preserve postfix side-effect semantics)

## 3. MVP Pipeline Roadmap

```
Real C input / function unit
   │
   ├─ Scoring mainline: C2Rust baseline → verified unsafe baseline → agent safety-refactoring loop
   │                                      │                         │
   │                                      └─ C oracle / Rust replay / diff / unsafe ledger
   │                                                                │
   │                                                                └─ repair/retry ≤ 5 + workflow metrics
   │
   └─ Supporting lane: clang AST dump → typed IR → bounded Rust candidate / fail-closed diagnostics
```

Current P0 follows the two scoring mainlines: first prove that a real unit can reach a verified unsafe baseline, then prove that the agent can reduce unsafe while the oracle stays green, and package that before/after translation-quality improvement as a reproducible harness artifact. The typed-IR lane continues to provide bounded candidates, diagnostics, negative coverage, and capability ledgers, but it is no longer the default P0 coverage target.

## 4. P0/P1/P2 Backlog (Default Execution Order)

### P0: Core Translation Capability x Harness Architecture

Execute P0 in this internal order. Do not bypass the scoring mainline just because handwritten-emitter coverage, file splitting, or governance cleanup is easier. Every externally assessable milestone must answer both questions: whether the translation result is safer/more readable than the baseline while remaining semantically equivalent, and whether the harness can automatically prove, repair, roll back, and reproduce that process.

1. First pick one real unit that is most likely to converge and easy for judges to understand. Default to the FlashDB competition-pinned `fdb_calc_crc32`; if C2Rust/toolchain work blocks, immediately switch to zlib-ng `adler32` as the safety-refactoring demo unit. The goal is not to expand the function set; it is to get one real before/after quickly.
2. Run that unit through C2Rust -> compile -> C oracle/Rust replay/diff verified unsafe baseline. Without a verified unsafe baseline, there is no judge-visible translation-correctness or harness-robustness story.
3. Run the agent safety-refactoring loop: each OpenCode/LLM worker round proposes exactly one minimal unsafe-reduction patch, then the harness applies it, compiles, runs oracle diff, checks unsafe delta, and either accepts it or rolls back to last-good and retries with a repair hint. The default cap remains 5 rounds. The first target is at least one accepted patch that preserves equivalence and strictly reduces unsafe.
4. Turn that before/after into a harness architecture exhibit: the planner/worker/verifier/repairer/reporter stage contracts, workflow trace, repair history, rollback evidence, final summary, and reproduction command must tell one coherent autonomous-repair story.
5. In parallel, emit a workflow metrics artifact that replaces checklist percentages: `units_total`, `units_converged`, `units_baseline_only`, `unsafe_reduction`, `avg_repair_rounds`, `auto_recovery_rate`, `human_interventions`, `always_compiles`, `always_equivalent`, `fail_closed_count`, wall clock, LLM calls, and per-unit status.
6. typed IR / generic emitter is only supporting infrastructure: use it for trivial fast paths, diagnostic comparison, bounded candidates, or blockers on the current before/after harness path. Do not expand Phase 2/3/4 for coverage's sake. Planner + multiple workers expand only after the first unit converges. Large-file splits, OpenSpec/evidence cleanup, release tags, and review gates come last with WIP/time boxes.

## 5. Current Core Principles

1. **The harness loop is the current scoring mainline**. C2Rust provides breadth, OpenCode/LLM workers provide safety-refactoring intelligence, and the C oracle/Rust replay/diff/unsafe ledger/evidence chain provide proof.
2. **C oracle is the sole ground truth**. typed IR, clang lowering, C2Rust output, LLM patches, and Rust candidates are only candidates or intermediate artifacts.
3. **Fail-closed**. When uncertain, refuse translation or roll back to the verified unsafe baseline, record reasons, never pretend success.
4. **Auditable evidence chain**. Every decision step has machine-readable evidence, cross-checked by the validator.
5. **Route only controls candidate path**. Semantic acceptance is decided by validation profile + gates.
6. **IR describes C, does not predict Rust**. Rust type inference and ownership inference are the responsibility of lowering or the agent safety-refactoring layer; typed IR is supporting infrastructure, not the current P0 coverage mainline.
7. **No restoration of specialty fallbacks**. Old crc32 templates and canned recognizers are deleted; project-specific code must not be reintroduced.
8. **Honest boundaries are more credible than exaggerated demos**. All documentation must honestly list "currently supported" and "explicitly unsupported".
