# Future Vision and MVP Roadmap

Chinese original: `future-vision-and-mvp.md`.

## 1. Goal

Build an end-to-end MVP pipeline: `input.c` → `c2rust-migrator` → `output.rs`. Phase 1 proof is complete in the code path sense (the FlashDB `real-fdb-calc-crc32` named slice can generate a compilable Rust candidate through real clang AST dump lowering + typed IR + generic emitter and bind it to semantic gates through accepted evidence), and committed evidence now includes a durable real-clang lowering artifact. Generated drafts remain candidates, and significant gaps remain before reaching an industrial-grade C→Rust translator.

The boundary must stay explicit: `validation/evidence/*/l1-native-build.json` only proves the original C project builds or smoke-tests in a pinned environment. It does not prove Rust translation success. Current real auto-translation capability is still concentrated in curated function slices; the large-project evidence catalogue is an input pool and baseline, not proof that real large projects can already be translated.

**2026-06-30 scoring-oriented pivot**: the current competition primarily scores two things: core translation capability and harness architecture. "Core translation capability" no longer means handwritten-transpiler C syntax coverage. It means the system's actual C-to-Rust output quality: C2Rust/candidate baseline -> verified unsafe baseline -> agent safety-refactoring before/after -> oracle equivalence proof -> reduced unsafe count. The harness architecture owns automatic orchestration, repair, rollback, measurement, and reproduction for that chain. The P0 mainline is therefore: C2Rust provides breadth, OpenCode/LLM workers provide safety-refactoring intelligence, and the existing C oracle / Rust replay / diff / unsafe ledger / evidence chain provide the ground-truth loop. typed IR / generic emitter is downgraded from the main battlefield to a trivial fast path, diagnostic comparator, and bounded candidate source. Phase 2/3/4 items such as CFG, union, switch/goto, compositional expression lowering, and full IR layering remain technical debt and long-term capability work, but they must not displace the current P0 dual mainline.

- **Run the judge-visible before/after before expanding translator coverage**: before adding a schema, manifest, gate, or typed-IR rule, explain how it advances the end-to-end harness: real C input -> C2Rust/candidate baseline -> oracle equivalence verification -> agent safety patch -> repair/retry -> unsafe reduction / workflow metrics / evidence.
- **Core translation capability and harness architecture must be proven by the same artifact**: a harness ledger, route report, or governance percentage alone is not enough; a one-off translation output alone is not enough either. Public milestones must include the original unsafe Rust, final Rust, accepted patch/step log, C/Rust diff-pass evidence, unsafe before/after counts, repair/retry trace, and reproduction command.
- **Governance must bind to workflow or capability growth**: every round of governance, documentation, schema, evidence, or OpenSpec work must also bind at least one verifiable payoff: an end-to-end harness blocker removed, C2Rust baseline traceability improved, agent repair/retry convergence improved, unsafe-monotonic evidence improved, a real C named slice candidate/accepted status advanced, an explicit fail-closed classification added, or a competition-environment reproducibility blocker removed. Pure governance cleanup may only run inside a fixed WIP/time box and must not substitute for the P0 harness loop and real-run artifacts.
- **FlashDB is only a use case**: FlashDB remains useful as a regression sample, but the project must not add FlashDB-specific recognizers, templates, or special-case routes.
- **Candidate generation is not semantic acceptance**: typed IR, C2Rust, LLMs, and handwritten rules are only candidate sources. Semantic pass is owned by the C oracle, Rust replay, diff, negative diff, unsafe ledger, and final verification.
- **The C oracle has boundaries too**: an oracle only proves behavior for a pinned source commit, fixture set, compiler/flags, target ABI, platform model, and observable-output contract. Undefined behavior, implementation-defined behavior, hardware/RTOS/volatile effects, and insufficient test coverage must be recorded explicitly instead of being hidden behind "tests passed."
- **Fail-closed must not become a dead end**: every refusal must include an actionable next step: source span, unsupported construct, missing IR/lowering rule, oracle/fixture gap, candidate sources worth trying, and human-review input. Otherwise it is only blocked, not a governance success.
- **Evidence cost must be governed**: release-required evidence, developer smoke evidence, diagnostic logs, and historical archives need separate classes. New evidence-producing paths must record runtime, file size, retention/compression/prune policy, so metadata growth does not consume translation-development capacity.
- **Unsafe numbers are not safety proof**: the unsafe budget is a governance metric, not proof that FFI, hardware, volatile, ABI, or concurrency semantics have been safely modeled. Zero findings only means no first-party non-test `unsafe` was found in the current scan scope.
- **C2Rust baseline must stay traceable**: the route/profile C2Rust candidate is only `candidate_context_only` and must bind the baseline manifest. When the baseline actually generates output, it must also bind output path/status/sha256 plus compile-only status, and the validator must reject output/compile evidence drift.
- **C2Rust skipped must not count as candidate success**: when the baseline is `skipped`, `blocked`, or has no output, it must record reason, toolchain/env, input hash, and `output_ref=null`; skipped baselines must not count as generated, compiled, accepted, or semantic pass.
- **Competition environment config is an adaptation reference and evidence profile**: `config/competition-env/environment.json` is the current default competition environment entrypoint. Development should follow its Ubuntu, Rust, Python, Node, gcc, mirror, and missing-tool constraints. The local machine does not need to replicate that environment exactly, but new default build, test, and validation paths must not violate it; `validation/environment-profiles/...` is a README-only historical reference and must not be used as a new executable configuration entrypoint.
- **Environment evidence needs proof classes**: only a real run on the competition host may be marked `competition-exact`; GitHub Actions or other Linux CI may only be marked `ci-approximation`; WSL/local Ubuntu may only be marked `wsl-local-simulation` or `local-simulation`. All three are useful for development, but they are not interchangeable proof levels.
- **Public reproduction paths default to Linux/CI**: PowerShell/Windows commands may remain as local convenience entrypoints, but externally assessable quickstarts, verification, and evidence generation must provide competition Linux/CI equivalents. When no equivalent path exists, mark the command as local-only.
- **OpenCode competition runs prioritize accuracy**: 600 minutes is only an external evaluation budget or upper-bound reference, not the optimization target. If no such cap exists, use the same evidence gates and prefer higher accuracy. Competition-facing agent evidence may come only from OpenCode invoking GLM-5.1; Codex, other OpenCode models, or local `local-simulation` runs are development aids only and must not close H9 or be described as competition-facing evidence. A single OpenCode interaction may use parallel agents or batch workers for independent slices, but each worker must have isolated output directories, repo-relative evidence, and independent status. Acceptance still comes only from the common validator/final verification, never from an agent's conversational judgment.
- **Evidence must be portable**: new evidence, manifests, cache metadata, and log references should prefer repo-relative paths, profile ids/hashes, and artifact hashes. Local `C:\...`, `F:\...`, or `/mnt/c/...` paths may appear only as diagnostic host metadata, not as reproducible entrypoints or cross-machine claim anchors.
- **Default paths must expose real capability**: no-clang default CI or competition paths must not present a legacy string translator success as typed-IR success. When typed IR did not run because `CLANG_PATH`, project-local vendored clang, or another tool is missing, evidence, metrics, and public claims must mark it as unavailable or compatibility fallback.
- **Project-local clang is only a candidate source, not a verified fact**: declaring search paths such as `tools/llvm/bin/clang*` or `tools/clang/bin/clang*` only means clang may be placed inside the project. The lane may be marked available only after `toolchain-check.sh` or equivalent Linux/WSL/CI evidence proves the binary, `-print-resource-dir`, a minimum TU AST dump containing `stdint.h`/`stddef.h`, and include search paths. If the repository does not contain an actual vendored clang bundle or that smoke has not been run, public status must say missing or unverified.
- **Handoff docs must stay short and auditable**: `CONTEXT.md` is only for current state, latest verification, and next-step handoff. Long session logs should be split or archived under `docs/c2rust-migration-agent/archive/`, and must not become release documentation, an external evaluation entrypoint, or capability proof.
- **Docs must stay bilingual**: maintained Chinese documentation must start with the repository-standard first line that points to its sibling `.en.md` mirror, and that mirror must exist in the same directory. Run `python3 -B -m unittest validation.tools.test_doc_mirror_contract` whenever documentation is added or edited. Update the Chinese original `future-vision-and-mvp.md` and this English mirror together.

## 2. IR Layering Design (Recommended Industrial Standard)

Key principle: **IR must not "decide how Rust should be written"; it must only "describe what C is"**. Correctness comes from C oracle; IR is the intermediate representation that faithfully describes C semantics.

### Layer 1: Semantic IR (Most Important)

**Preserve C semantics. Do not do Rust inference. Do not produce candidates.**

This layer is the translator's core asset. It only answers: "What does this C code do in the C abstract machine?"

- Every C operation preserves its original semantics: integer promotion rules, usual arithmetic conversions, sequence points, lvalue conversions
- No premature judgment on "this pointer can become a slice" or "this struct can become a Rust struct"
- Preserve raw pointer arithmetic, implicit casts, truncation, and promotion information
- Array-to-pointer decay is part of C semantics and must be preserved in the IR
- UB markers (locations of undefined behavior) must also be recorded at this layer

**Current status**: Our typed IR mixes in some Rust inference (e.g., directly marking `const void *` as `&[u8]`). This is acceptable for P0 but should be separated into a dedicated Lowering layer long-term.

### Layer 2: Control IR

**if / loop / goto / switch, with explicit CFG.**

- Control flow transitions from AST to explicit basic blocks + CFG
- `if-else`, `while`, `for`, `do-while`, `switch-case`, `goto`/label all enter a unified CFG
- Each edge carries an explicit condition (or is unconditional)
- `break` and `continue` map to CFG edges; no ad-hoc handling needed
- Support relooper (recovering high-level structured control flow from arbitrary CFG), which is prerequisite for translating `goto` / `switch`

**Current status**: We have a basic `cfg.json` evidence template, but typed IR internally still uses AST-style control flow (`If`, `While`, `For`, `DoWhile`). Rust candidate lowering for `switch`, `goto`, and computed goto is still unsupported. The legacy compatibility path has started recording minimal CFG/fail-closed evidence for label/goto/switch/case/default, but that is not full Control IR and does not replace clang AST / typed-IR fixture replay, route evidence, or a relooper.

### Layer 3: Typed Value IR

**integer / pointer / struct / array, explicit casts only.**

- All implicit type conversions (integer promotion, usual arithmetic conversion, array-to-pointer decay, function-to-pointer decay) become **explicit casts** at this layer
- Pointer arithmetic is decomposed into element access: `p + i` becomes `element_at(p, i)` or equivalent
- Struct field access is explicit offset-based or symbolic field access
- Array indexing is explicit base + offset
- The type system only describes C runtime behavior; no Rust type inference

**Current status**: Our typed IR has `Cast { implicit }` to distinguish explicit/implicit casts, integer types have signed/width information, and pointers have `Pointer { pointee }`. The clang frontend now tightens unknown/missing `ImplicitCastExpr.castKind` to `Unsupported`/fail-closed, modeled `IntegralCast`/`IntegralPromotion` nodes can be preserved as explicit IR casts in ordinary value contexts, binary usual-arithmetic contexts, unary-plus integer-promotion contexts, direct-call argument contexts, `?:` condition contexts, and `if`/`while`/`do-while`/`for` condition contexts, integer `NoOp` in preserved value contexts is preserved as an explicit `implicit=true` IR cast, and explicit C-style same-width integer `NoOp` casts remain explicit `implicit=false` casts. Ordinary expression-position `ArrayToPointerDecay` and ordinary value/argument-position `FunctionToPointerDecay` now lower into explicit typed IR as `IrExpr::ArrayToPointerDecay` / `IrExpr::FunctionToPointerDecay`; unary deref of a direct complete fixed array DeclRef lowers to `array[0]`, restricted `*(array + integer_expr)` lowers to `array[index]`, while other ordinary expression, pointer-value, or function-pointer-value shapes still fail closed during Rust emission or bounded-call validation without explicit lowering evidence. Clang-proven integer value-context `LValueToRValue` is now preserved as an explicit typed IR `IrExpr::LValueToRValue` node; this currently covers only integer scalar reads such as `return value;`. Pointer, record, and general lvalue reads must still use existing narrow dedicated paths or fail closed without ownership, lifetime, alias, layout, or provenance lowering evidence, and non-integer/non-preserved `NoOp` remains a limited transparent skeleton boundary. It still does not route every implicit cast through one unified Semantic IR node; array/function decay lowering, non-integer conversions, and full conversion discipline across parameters, returns, and compound assignments still need further formalization.

### Lowering Layer (from Semantic IR to Rust candidate)

This layer converts "describing C" into "generating Rust". Key principles:

1. Do not modify the Semantic IR itself
2. Every lowering rule must be provable (supported by C oracle or typed evidence)
3. When lowering fails, preserve the complete fail-closed reason
4. No "guessing" allowed — if C semantics cannot be safely mapped to safe Rust, refuse translation

Typical lowering rules:
- `const T *p` + read-access evidence (`*p` / `p[i]` / `*(p+i)` / `*p++`, etc.) → `p: &[T]` (must prove: an actual read access exists, no writes, no escape, bounded lifetime, and inferrable length/index bounds; an unused or declared-only readonly pointer parameter fails closed and must not auto-lower)
- `T *out` + write-only access → `out: &mut [T]` (requires noalias proof; if the same function also reads from readonly `const T *`, there must be explicit `restrict`/noalias/escape facts, and `const` alone must not imply non-aliasing)
- `uint32_t + uint8_t` → explicit `(byte as u32) + acc` (requires promotion proof)
- `while(size--)` → Rust `loop` + `wrapping_sub` (must preserve postfix side-effect semantics)

## 5. Current Core Principles

1. **The harness loop is the current scoring mainline**. C2Rust provides breadth, OpenCode/LLM workers provide safety-refactoring intelligence, and the C oracle/Rust replay/diff/unsafe ledger/evidence chain provide proof.
2. **C oracle is the sole ground truth**. typed IR, clang lowering, C2Rust output, LLM patches, and Rust candidates are only candidates or intermediate artifacts.
3. **Fail-closed**. When uncertain, refuse translation or roll back to the verified unsafe baseline, record reasons, never pretend success.
4. **Auditable evidence chain**. Every decision step has machine-readable evidence, cross-checked by the validator.
5. **Route only controls candidate path**. Semantic acceptance is decided by validation profile + gates.
6. **IR describes C, does not predict Rust**. Rust type inference and ownership inference are the responsibility of lowering or the agent safety-refactoring layer; typed IR is supporting infrastructure, not the current P0 coverage mainline.
7. **No restoration of specialty fallbacks**. Old crc32 templates and canned recognizers are deleted; project-specific code must not be reintroduced.
8. **Honest boundaries are more credible than exaggerated demos**. All documentation must honestly list "currently supported" and "explicitly unsupported".
